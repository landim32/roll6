# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project status

The backend (feature `001-backend-core-entities`) is implemented in `backend/`; the frontend does not exist yet. There is no PostgreSQL or Docker on the dev machine, so migrations are generated but must be applied against a reachable database (`dotnet ef database update`, see below). Image URLs need S3 credentials (standard AWS env vars/profile) because reads generate presigned URLs.

## Product intent

Roll6 is a deliberately **simple** Roll20-style virtual tabletop web app. Scope:

- User login.
- Users create adventure maps.
- Users upload images (map backgrounds, token art).
- Users create tokens and place/move them on the map.
- Maps use a grid built with the hexagon algorithms from Red Blob Games: https://www.redblobgames.com/grids/hexagons/

Keep it simple — resist adding Roll20 features (dynamic lighting, character sheets, macros, chat, etc.) unless a spec explicitly asks for them.

## Constitution

`.specify/memory/constitution.md` is binding and overrides agents/skills when they conflict. Read it before planning or implementing. Highlights that are easy to get wrong:

- New entities MUST be built with the `dotnet-architecture` (backend) and `react-architecture` (frontend) skills — don't hand-roll those patterns.
- Frontend: Bootstrap 5 (not Tailwind/shadcn, even though the `ux-designer` agent defaults to them), Context API only (no Redux/Zustand), Fetch API for new services, `interface` over `type`, `VITE_` env vars.
- Directory casing is load-bearing: `Contexts/`, `Services/` uppercase; `hooks/`, `types/` lowercase.
- Never run `docker` / `docker compose` locally.
- PostgreSQL via EF Core only; snake_case tables/columns, `ClientSetNull` deletes (never Cascade).
- Auth token is stored in localStorage (never cookies); sensitive controllers need `[Authorize]`.

## Hex grid rules (Red Blob Games, constitution Principle VII)

All grid math must follow the Red Blob Games hexagon guide rather than ad-hoc formulas:

- Hexes are always **flat-top** in a rectangular grid (`grid_width` columns × `grid_height` rows, odd columns shifted half a hex down — the guide's "odd-q" offset layout).
- Positions are **stored as column/row** (`x`, `y`). For distance, neighbors, lines and ranges convert to axial (`q = x`, `r = y - (x - (x & 1)) / 2`), compute with the cube/axial formulas, and convert back (`x = q`, `y = r + (q - (q & 1)) / 2`). Never store `q`/`r`/`s`.
- Hex↔pixel conversion goes through a `Layout` (size, origin) as described in the guide's "Implementation" section.
- Pixel→hex uses fractional hex + **cube rounding** (`hex_round`); never round q/r independently.
- Distance, neighbors, line drawing (lerp + round), and ranges come from the guide's cube/axial formulas.
- Keep the hex math in one pure, framework-free module (frontend) so it can be unit-tested and, if the backend needs grid logic, mirrored 1:1 in C#.

## Backend layout and commands

Solution lives in `backend/` (`Roll6.sln`): `DTO` → `Infra.Interfaces` → `Domain` → `Infra` → `Application` (centralized DI in `Startup.cs`) → `API`, plus `Roll6.Mcp` (MCP gateway, depends only on `DTO`) and `Roll6.Tests` (xUnit + Moq + FluentAssertions, domain services only). Design docs: `specs/001-backend-core-entities/`.

- Users are local (`users` table, `PasswordHasher` PBKDF2); login issues our own JWT, sent as `Authorization: Bearer`. Controllers take the owner id from the JWT `sub` claim (`CurrentUserId`) and pass it to services, which enforce ownership.
- Error flow: services throw domain exceptions and every controller action wraps its body in `try { } catch (Exception ex) { return HandleException(ex); }` (`ApiControllerBase`): `DomainValidationException` → 400 `ValidationProblemDetails`, `UnauthorizedAccessException` → 403, `KeyNotFoundException` → 404, `ConflictException` → 409, anything else → `StatusCode(500, ex.Message)`. Never throw `InvalidOperationException` for business conflicts — EF Core throws it on connection failures.
- Responses follow the ASP.NET Core default: DTO returned directly on success, `ProblemDetails` on errors (constitution v3.0.0). No custom envelope — ignore the `sucesso`/`mensagem`/`erros` shape in the `react-architecture` skill. Paged lists use `PagedList<T>` with `PageQuery` (`page`, `pageSize` ≤ 100, `search`).
- Images: stored in DigitalOcean Spaces through the AWS S3 SDK (`S3:ServiceUrl` = `https://{region}.digitaloceanspaces.com`, `S3:Region` = `us-east-1` signing region, `ForcePathStyle` false; empty `ServiceUrl` means AWS S3). For custom endpoints the client disables default checksums and chunked uploads, which S3-compatible providers may reject. Upload once via `POST /api/image` (`IImageStorageAppService`); files go to `{S3:Folder}/{guid}.{ext}` (`S3_FOLDER` in the env files, default `roll6`); entities store only `{guid}.{ext}` (validated by `Guard.ImageFileName`) and the storage service adds the folder, reads return presigned URLs. The bucket sends no CORS headers, so the map-share canvas reads stored images through `GET /api/image/file/{fileName}` (`[Authorize]`, name must be `{32-hex}.png|jpg|webp`, streamed from the bucket via `IImageStorageAppService.OpenAsync`; excluded from the MCP catalog) — `lib/mapSnapshot.loadImage` extracts the name from the presigned URL (`storedImageName`) and only falls back to a direct `crossOrigin` load for other URLs. Character sheet files (feature 022) use `POST /api/document` (`DocumentController` → `IImageService.UploadDocumentAsync`): PNG/JPEG/WebP **or PDF** (signature `%PDF-`), ≤ 10 MB, bytes stored untouched with the original Content-Type, response `{ fileName, url, type: image|pdf }`; `characters.sheet_file` holds the name (`Guard.SheetFileName`, `.pdf` allowed only there), sent as `sheetFile` in `POST`/`PUT /api/character` (omitted on PUT = removed) and read as `sheetFileUrl`/`sheetFileType` (`SheetFiles.TypeOf`) in `CharacterInfo`. Since feature 032 each participation has its own `campaign_characters.sheet_file`, copied from the character when it joins and read as `sheetFile`/`sheetFileUrl`/`sheetFileType` in `CampaignCharacterDetailInfo` (owner, master, approved participants) — stored files are write-once `{guid}.{ext}` and nothing ever overwrites or deletes them, so the campaign "copy" is a second reference to the same object, not a second blob (that is also what makes replacing or removing one side leave the other untouched).
- Campaign characters (feature 005/008): `GET /api/character/search` is public to logged users and returns only `CharacterSearchInfo` (name, image, owner) — never the sheet/stats; `GET /api/campaign/{id}/character` stays master/approved-only, and players read their own statuses via `GET /api/campaigncharacter/mine`; `DELETE /api/campaigncharacter/{id}` (master) removes the participation only. `CampaignCharacter.RequestAccess(..., autoApprove)` approves directly in open campaigns and when the requester is the campaign master.
- Life/energy, status and sheet per campaign (features 009/010): `characters.life`/`energy` are the **totals** (≥ 0) and the character has no status. Each participation holds `current_life`/`current_energy` (≤ total, may be ≤ 0; life does not set posture), `character_status` (free text ≤ 260 — `CharacterStatus`, not the participation `Status` enum) and `sheet`/`sheet_file` = the **campaign sheet** ("Ficha da Campanha", feature 032): a copy of the character's sheet and sheet file taken when the participation joins, changed only here afterwards and never re-synced (032 reverted the 023 "campaign notes", which started empty). Whenever a participation is created or becomes Approved, `CampaignCharacter.ResetFrom(character)` sets the currents to the totals, copies `Sheet`/`SheetFile` from the character and clears the status (the service passes the `Character` into `RequestAccess`/`CreateInvite`/`Invite`/`AcceptInvite`/`ApproveRequest`) — that is the only copy point, there is no re-sync action; migration `AddCampaignSheetFile` backfilled existing rows with the character's sheet plus the old notes appended under an "Anotações anteriores da campanha" heading (nothing discarded). `CampaignCharacter.ChangeSheetFile` takes null = keep, `""` = remove, a stored name = replace — a partial update, unlike `CharacterInsertInfo.sheetFile` where null removes. The MCP descriptions (`get_participation`/`update_participation`, `roll6://guide`) explain the campaign sheet; the turn-log diff key stays `"notes"` (historical `jsonb`) but `TurnSummary` now prints "Ficha da campanha alterada", plus "Ficha em arquivo alterada" for the file. `CharacterService.UpdateAsync` clamps the currents via `ClampVitalsAsync`. `GET`/`PUT`/`DELETE /api/character/{id}` are owner-only — the master never changes the character itself. Transfer (feature 021): `POST /api/character/{id}/transfer` (`{ email }`, owner only, 204) changes only `characters.user_id` through a conditional update (`CharacterRepository.TransferAsync`, `WHERE user_id = owner`; 0 rows → 409) — participations, pieces and turns point to the character and every player permission reads the current owner, so everything else stays; errors 400 (invalid e-mail / own e-mail), 404 (`Usuário não encontrado.`); afterwards `party.changed` + `mapTokens.changed` in each campaign and the former owner leaves the groups where they lost access. `PUT /api/campaigncharacter/{id}` (`CampaignCharacterUpdateInfo` → `UpdatePlay` + `ChangeSheetFile`, Approved only; optional `tokenId` saved on the character via `Character.ChangeToken`, null = keep; optional `sheetFile`, null = keep / `""` = remove / a stored name = replace) = owner or campaign master; `GET /api/campaigncharacter/{id}` (`CampaignCharacterDetailInfo`, with `sheet`/`sheetFile`/`sheetFileUrl`/`sheetFileType` = this campaign's, `characterSheet` read-only and `characterTokenName`/`characterTokenImageUrl`) = owner, master or any approved participant. Lists carry `characterStatus`/`characterMove` but not the sheet (they are polled).
- Maps are soft-deleted (`MapStatus.Deleted`); map names come from `MapRepository.InsertWithNextSequenceAsync` (unique index on campaign + model + sequence). Deletes of tokens/map models/campaigns in use are blocked in the services (FKs are `ClientSetNull`, never cascade); campaign deletion removes its Deleted maps inside `IUnitOfWork`.
- Slugs (029): `campaigns.slug` and `maps.slug` are `varchar(100)`, globally unique (`ix_campaigns_slug`, `ix_maps_slug`), required, and immutable — `AssignSlug` runs only on insert (`Slug.From` + `Slug.NextFree`, retry once on `UniqueViolation` of that index; maps also retry the sequence index). Reads include `slug`. `GET /api/campaign/slug/{slug}` is any logged user (404 `Campanha não encontrada.`); `GET /api/map/slug/{slug}` is master or approved (Deleted → 404 `Mapa não encontrado.` before the access check; no access → 403). `GET /api/campaign/table` lists campaigns the user masters or plays with an approved character, plus the active current map (`CampaignTableInfo`). `GET /api/campaign/{id}/turn/narration?turnNo=` (master or approved) joins `TurnType.Narration` entries of that turn — or, without `turnNo`, of the greatest `turn_no < current_turn` that has one — with `\n\n`; `finishedAt` is the last entry's `created_at` (null on the turn in progress); none → 204. MCP: `get_campaign_by_slug`, `get_map_by_slug`, `list_my_table_campaigns`, `get_turn_narration`. Migration `AddSlugs` backfills in SQL (`database/migrations/029-slugs.sql`).
- NPCs (feature 013, backend only): `Npc` is the owner's library entry (required `TokenId`, same limits as `Character`, optional `status` ≤ 260 copied to each new `MapNpc`; `/api/npc` CRUD owner-only, delete refused while in a campaign). `CampaignNpc` makes one of the master's own NPCs available in a campaign (unique per campaign; `POST`/`DELETE /api/campaignnpc` master only; list `GET /api/campaign/{id}/npc` for the master and approved participants). `MapNpc` is one occurrence on a campaign map with its own name, status and **current** life/energy (`map_npcs.current_life`/`current_energy`, feature 026; start at the NPC's totals, may go ≤ 0, never above the NPC's `life`/`energy` — `MapNpcInfo` returns `currentLife`/`currentEnergy` + `totalLife`/`totalEnergy`, `PUT /api/mapnpc/{id}` takes `currentLife`/`currentEnergy`; lowering the NPC's totals clamps its occurrences via `IMapNpcRepository.ClampVitalsAsync` and publishes `mapTokens.changed`); `POST /api/mapnpc` creates it **and** its piece (`MapToken.PlaceNpc`, Npc type, the NPC's token, free hex inside the grid) in one transaction, linked by `map_tokens.map_npc_id` (unique) like `campaign_character_id`; pieces with `MapNpcId` show the occurrence's data (never the piece's own life/energy/status, which stay 0 for NPC pieces — no copy is kept): `MapTokenInfo` = occurrence name/current vitals/status + the NPC's totals (`totalLife`/`totalEnergy`, also filled for characters and objects), move and sheet (the piece's own sheet wins when set). Deleting the occurrence deletes the piece and vice versa; removing a `CampaignNpc` deletes its occurrences and pieces on the campaign's maps; campaign deletion also removes `campaign_npcs` and the `map_npcs` of its deleted maps; tokens used by NPCs can't be deleted. Turn log (024): every entry has a required `user_id` (author; old entries were filled with the character owner for moves/actions, else the master), moves store `moved` (movement points, computed with `HexGrid.MovementCost` also for the master, ignoring pieces when there is no free path) and `TurnType.CharacterUpdate` (4) entries store `changes` (`jsonb` `[{ field, before, after }]`, `TurnChange.Diff`) — created only by the system, in the same transaction, when something actually changed: `CampaignCharacterService.UpdateAsync` (currentLife, currentEnergy, characterStatus, notes), `MapNpcService.UpdateAsync` (name, life, energy, status) and `CharacterService.UpdateAsync` (name, life, energy, move — one entry per campaign where the character is approved). Turn data/processing for AI assistants (027, `TurnService.Processing.cs`, API + MCP only): `GET /api/campaign/{id}/turn/data?turnNo=` (master or approved) returns `TurnDataInfo` — approved characters (player, current/total life and energy = fatigue, status, x/y/look/lookName of the piece on the current map), NPC occurrences of the current map (same fields) and `actions` (`TurnSummary.BuildActions`, same text as the summary; names/lines come from the shared `LoadNamesAsync`/`BuildLines`). `POST /api/campaign/{id}/turn/process` (master) takes `TurnProcessInfo { characters[{characterId,…}], npcs[{mapNpcId,…}], narration }` with optional currentLife/currentEnergy/status/clearStatus/x/y/look, validates the whole batch first (same rules as the single updates, positions on the final state so pieces may swap, errors keyed `characters[i].field`/`npcs[i].field`/`batch`/`narration`), then in one transaction saves participations/occurrences/pieces, logs `CharacterUpdate` and `Movement` (no one-move limit) by the master and a `TurnType.Narration` (5, no actor, `description` ≤ 10000 — the column grew; actions stay ≤ 2000) and **finishes the turn**; publishes `party.changed`, `mapTokens.changed`, `turn.finished` and returns `{ finishedTurn, turnNo, data }`. - MCP server (feature 020): separate project **`Roll6.Mcp`** (own container `roll6-mcp`, `Roll6.Mcp/Dockerfile`, dev `dotnet run --project Roll6.Mcp` on http://localhost:5129) exposing the API to AI assistants at `/mcp` (Streamable HTTP, `ModelContextProtocol.AspNetCore` 2.x). It is a **thin gateway**: it references only `Roll6.DTO` and holds no database, S3 or JWT secrets — every tool is one REST call to the API (`Roll6Api:BaseUrl`, `http://api:8080` in containers) through `Roll6ApiClient`, which forwards the caller's `X-Api-Key` (or `Authorization`), so permissions, validation, results and the real-time events (017) are the API's. `ApiCredentialGate` answers 401 on `/mcp` without a credential the API accepts (checked via `GET /api/user/me`, cached 60 s). `McpToolRunner.FromResponseAsync` turns the API response into the tool result: JSON as text + `structuredContent` (lists inside `{ items }`, 204 → `{ ok: true }`), errors → `isError` with the API's problem details (plain-text/empty bodies get `status`/`detail`). Each tool (`Tools/*.cs`, `[McpServerToolType]`) carries `[ApiOperation("VERB", "/api/route")]`, an English `[Description]` with *What it does / Who can use it / Returns / Common errors / Related tools*, described parameters (`McpDocs`) and `ReadOnly`/`Destructive`/`Idempotent` annotations; `Roll6Guide` is the resource `roll6://guide`, the tool `get_roll6_guide` and the server instructions. **Adding or changing an endpoint requires its tool**: `Roll6.Tests/Mcp/McpCoverageTests` (every controller action except the 8 login-only ones has exactly one tool), `McpRouteParityTests` (each tool sends its `ApiOperation` verb/route with the caller's key, via `FakeApi`) and `McpDescriptionTests` guard it. Client setup: `claude mcp add --transport http roll6 https://{domain}/mcp --header "X-Api-Key: r6_…"`. The `web` nginx proxies `/mcp` to `mcp:8080`; the Vite dev server to `VITE_MCP_PROXY` (5129).

## Frontend layout and commands

React SPA in `frontend/` (design docs: `specs/006-frontend-map-editor/`). Dark theme only (`data-bs-theme="dark"` on `<html>`), every window besides the map is a modal, all feedback via `sonner` toasts, all texts via i18next (`src/i18n/locales/pt-BR.json`).

- Folder casing is from the constitution, not from the `react-architecture` skill: `src/Contexts/`, `src/Services/`, `src/hooks/`, `src/types/`. ## Recent Changes
- 032-campaign-sheet-copy: each participation owns a copy of the character sheet — `campaign_characters.sheet` (replacing the 023 notes) and the new `campaign_characters.sheet_file` — taken by `ResetFrom` when the character joins or returns to Approved and never re-synced. Owner and master change that copy (`ChangeSheetFile`: null keeps, `""` removes, a stored name replaces); the master still cannot touch the character, and the "copy" is a second reference to the same write-once stored object, not a second blob. `sheetFile`/`sheetFileUrl`/`sheetFileType` in `CampaignCharacterDetailInfo` are now the campaign's, `characterSheet` stays read-only. The character form split into `CharacterFormModal` (character, now also editable from the pencil in `SelectCharacterModal`) and `CampaignCharacterModal` (campaign, from a party card); tab renamed "Ficha da Campanha", and it says `sheetFile.noneCampaign` instead of falling back to the character's file. Migration `AddCampaignSheetFile` backfills the copy and appends the old notes under a heading (nothing discarded). Turn log keeps the `"notes"` diff key with the label "Ficha da campanha alterada" and adds `"sheetFile"`. MCP `update_participation` gains `sheetFile` (still 86 operations / 87 tools)
- 031-token-posture-footprint: posture (Em pé / Caído / Fora de combate) of characters (per campaign) and NPC occurrences, changed by the owner/master on the piece menu, API and MCP (`set_piece_posture`, 87 tools), logged in the turn; down pieces lie, out-of-combat ones are also black and white; tokens take 1, 2, 3, 7 or 10 hexes (`HexGrid.Footprint`, `Occupancy`), the whole shape must fit to place/move/turn, and lying down is never refused (overlap until the piece moves)
- 030-turn-log-admin (API + MCP only): the master fixes the turn log — `PUT /api/turn/{id}` (partial update of any entry), `POST /api/turn` with all five types in any turn up to the current one (actor/map must be of the campaign), and `PUT /api/campaign/{id}/turn/current` (forward = finish, back = 409 unless `discardLaterEntries`); nothing moves pieces or changes values. MCP 86 tools: `update_turn_entry`, `set_current_turn`
- 029-slug-routes-map-share: immutable global slugs on campaigns and maps; `/campaign/:slug` and `/map/:slug` synced only by `useTableRoute` (restore of `roll6:campaign`/`roll6:map` only on `/`); `TableSelect` replaces the two menu selectors (`GET /api/campaign/table`); the turn-finished window shows only the narration; Share draws the map to a JPEG and sends the latest narration as WhatsApp text (`GET /api/campaign/{id}/turn/narration`). MCP 84 tools: `get_campaign_by_slug`, `get_map_by_slug`, `list_my_table_campaigns`, `get_turn_narration`
- 028-turn-console: chevron in the middle of the map footer opens a translucent turn console over the map (one block per turn, newest first, the turn in progress included and shown first, infinite list, live on turn finished) with a full-screen "Ampliar" window; `GET /api/campaign/{id}/turn/history` paged by turn number; MCP `get_turn_history`. The console lists only the master's `Narration` of a turn — moves, speech, action results and character changes are left out — and a turn without narration is not listed at all; the whole turn stays in `get_turn_summary`/`TurnLogModal`
- 027-turn-ai-processing: `GET /api/campaign/{id}/turn/data` (characters, NPC occurrences and the turn's actions in one call) and `POST /api/campaign/{id}/turn/process` (master: atomic batch of vitals/status/positions + narration, logged in the turn, then the turn is finished); new `TurnType.Narration`; MCP `get_turn_data`/`process_turn`; no frontend
