# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project status

The backend (feature `001-backend-core-entities`) is implemented in `backend/`; the frontend does not exist yet. There is no PostgreSQL or Docker on the dev machine, so migrations are generated but must be applied against a reachable database (`dotnet ef database update`, see below). Image URLs need S3 credentials (standard AWS env vars/profile) because reads generate presigned URLs.

## Product intent

Roll6 is a deliberately **simple** Roll20-style virtual tabletop web app. Scope:

- User login.
- Users create adventure maps.
- Users upload images (map backgrounds, token art).
- Users create tokens and place/move them on the map.
- Maps use a grid built with the hexagon algorithms from Red Blob Games: https://www.redblobgames.com/grids/hexagons/

Keep it simple — resist adding Roll20 features (dynamic lighting, character sheets, macros, chat, etc.) unless a spec explicitly asks for them.

## Constitution

`.specify/memory/constitution.md` is binding and overrides agents/skills when they conflict. Read it before planning or implementing. Highlights that are easy to get wrong:

- New entities MUST be built with the `dotnet-architecture` (backend) and `react-architecture` (frontend) skills — don't hand-roll those patterns.
- Frontend: Bootstrap 5 (not Tailwind/shadcn, even though the `ux-designer` agent defaults to them), Context API only (no Redux/Zustand), Fetch API for new services, `interface` over `type`, `VITE_` env vars.
- Directory casing is load-bearing: `Contexts/`, `Services/` uppercase; `hooks/`, `types/` lowercase.
- Never run `docker` / `docker compose` locally.
- PostgreSQL via EF Core only; snake_case tables/columns, `ClientSetNull` deletes (never Cascade).
- Auth token is stored in localStorage (never cookies); sensitive controllers need `[Authorize]`.

## Hex grid rules (Red Blob Games, constitution Principle VII)

All grid math must follow the Red Blob Games hexagon guide rather than ad-hoc formulas:

- Hexes are always **flat-top** in a rectangular grid (`grid_width` columns × `grid_height` rows, odd columns shifted half a hex down — the guide's "odd-q" offset layout).
- Positions are **stored as column/row** (`x`, `y`). For distance, neighbors, lines and ranges convert to axial (`q = x`, `r = y - (x - (x & 1)) / 2`), compute with the cube/axial formulas, and convert back (`x = q`, `y = r + (q - (q & 1)) / 2`). Never store `q`/`r`/`s`.
- Hex↔pixel conversion goes through a `Layout` (size, origin) as described in the guide's "Implementation" section.
- Pixel→hex uses fractional hex + **cube rounding** (`hex_round`); never round q/r independently.
- Distance, neighbors, line drawing (lerp + round), and ranges come from the guide's cube/axial formulas.
- Keep the hex math in one pure, framework-free module (frontend) so it can be unit-tested and, if the backend needs grid logic, mirrored 1:1 in C#.

## Backend layout and commands

Solution lives in `backend/` (`Roll6.sln`): `DTO` → `Infra.Interfaces` → `Domain` → `Infra` → `Application` (centralized DI in `Startup.cs`) → `API`, plus `Roll6.Mcp` (MCP gateway, depends only on `DTO`) and `Roll6.Tests` (xUnit + Moq + FluentAssertions, domain services only). Design docs: `specs/001-backend-core-entities/`.

- Users are local (`users` table, `PasswordHasher` PBKDF2); login issues our own JWT, sent as `Authorization: Bearer`. Controllers take the owner id from the JWT `sub` claim (`CurrentUserId`) and pass it to services, which enforce ownership.
- Error flow: services throw domain exceptions and every controller action wraps its body in `try { } catch (Exception ex) { return HandleException(ex); }` (`ApiControllerBase`): `DomainValidationException` → 400 `ValidationProblemDetails`, `UnauthorizedAccessException` → 403, `KeyNotFoundException` → 404, `ConflictException` → 409, anything else → `StatusCode(500, ex.Message)`. Never throw `InvalidOperationException` for business conflicts — EF Core throws it on connection failures.
- Responses follow the ASP.NET Core default: DTO returned directly on success, `ProblemDetails` on errors (constitution v3.0.0). No custom envelope — ignore the `sucesso`/`mensagem`/`erros` shape in the `react-architecture` skill. Paged lists use `PagedList<T>` with `PageQuery` (`page`, `pageSize` ≤ 100, `search`).
- Images: stored in DigitalOcean Spaces through the AWS S3 SDK (`S3:ServiceUrl` = `https://{region}.digitaloceanspaces.com`, `S3:Region` = `us-east-1` signing region, `ForcePathStyle` false; empty `ServiceUrl` means AWS S3). For custom endpoints the client disables default checksums and chunked uploads, which S3-compatible providers may reject. Upload once via `POST /api/image` (`IImageStorageAppService`); files go to `{S3:Folder}/{guid}.{ext}` (`S3_FOLDER` in the env files, default `roll6`); entities store only `{guid}.{ext}` (validated by `Guard.ImageFileName`) and the storage service adds the folder, reads return presigned URLs. Character sheet files (feature 022) use `POST /api/document` (`DocumentController` → `IImageService.UploadDocumentAsync`): PNG/JPEG/WebP **or PDF** (signature `%PDF-`), ≤ 10 MB, bytes stored untouched with the original Content-Type, response `{ fileName, url, type: image|pdf }`; `characters.sheet_file` holds the name (`Guard.SheetFileName`, `.pdf` allowed only there), sent as `sheetFile` in `POST`/`PUT /api/character` (omitted on PUT = removed) and read as `sheetFileUrl`/`sheetFileType` (`SheetFiles.TypeOf`) in `CharacterInfo` and in `CampaignCharacterDetailInfo` (owner, master, approved participants); it belongs to the character and is never copied to participations.
- Campaign characters (feature 005/008): `GET /api/character/search` is public to logged users and returns only `CharacterSearchInfo` (name, image, owner) — never the sheet/stats; `GET /api/campaign/{id}/character` stays master/approved-only, and players read their own statuses via `GET /api/campaigncharacter/mine`; `DELETE /api/campaigncharacter/{id}` (master) removes the participation only. `CampaignCharacter.RequestAccess(..., autoApprove)` approves directly in open campaigns and when the requester is the campaign master.
- Life/energy, status and sheet per campaign (features 009/010): `characters.life`/`energy` are the **totals** (≥ 0) and the character has no status. Each participation holds `current_life`/`current_energy` (≤ total, may be ≤ 0 = fallen), `character_status` (free text ≤ 260 — `CharacterStatus`, not the participation `Status` enum) and `sheet` = the **campaign notes** ("Anotações da Campanha": only what changed in the campaign compared to the character's sheet, e.g. a lost sword — never a copy of the sheet). Whenever a participation is created or becomes Approved, `CampaignCharacter.ResetFrom(character)` sets the currents to the totals and clears the notes and the status (the service passes the `Character` into `RequestAccess`/`CreateInvite`/`Invite`/`AcceptInvite`/`ApproveRequest`); migration `ClearCopiedCampaignNotes` dropped the old untouched copies. The MCP descriptions (`get_participation`/`update_participation`, `roll6://guide`) explain the notes. `CharacterService.UpdateAsync` clamps the currents via `ClampVitalsAsync`. `GET`/`PUT`/`DELETE /api/character/{id}` are owner-only — the master never changes the character itself. Transfer (feature 021): `POST /api/character/{id}/transfer` (`{ email }`, owner only, 204) changes only `characters.user_id` through a conditional update (`CharacterRepository.TransferAsync`, `WHERE user_id = owner`; 0 rows → 409) — participations, pieces and turns point to the character and every player permission reads the current owner, so everything else stays; errors 400 (invalid e-mail / own e-mail), 404 (`Usuário não encontrado.`); afterwards `party.changed` + `mapTokens.changed` in each campaign and the former owner leaves the groups where they lost access. `PUT /api/campaigncharacter/{id}` (`CampaignCharacterUpdateInfo` → `UpdatePlay`, Approved only; optional `tokenId` saved on the character via `Character.ChangeToken`, null = keep) = owner or campaign master; `GET /api/campaigncharacter/{id}` (`CampaignCharacterDetailInfo`, with `sheet` = notes, `characterSheet` read-only and `characterTokenName`/`characterTokenImageUrl`) = owner, master or any approved participant. Lists carry `characterStatus`/`characterMove` but not the sheet (they are polled).
- Maps are soft-deleted (`MapStatus.Deleted`); map names come from `MapRepository.InsertWithNextSequenceAsync` (unique index on campaign + model + sequence). Deletes of tokens/map models/campaigns in use are blocked in the services (FKs are `ClientSetNull`, never cascade); campaign deletion removes its Deleted maps inside `IUnitOfWork`.
- NPCs (feature 013, backend only): `Npc` is the owner's library entry (required `TokenId`, same limits as `Character`; `/api/npc` CRUD owner-only, delete refused while in a campaign). `CampaignNpc` makes one of the master's own NPCs available in a campaign (unique per campaign; `POST`/`DELETE /api/campaignnpc` master only; list `GET /api/campaign/{id}/npc` for the master and approved participants). `MapNpc` is one occurrence on a campaign map with its own name/life/energy/status (copied from the NPC; life/energy may go ≤ 0); `POST /api/mapnpc` creates it **and** its piece (`MapToken.PlaceNpc`, Npc type, the NPC's token, free hex inside the grid) in one transaction, linked by `map_tokens.map_npc_id` (unique) like `campaign_character_id`; pieces with `MapNpcId` show the occurrence's data. Deleting the occurrence deletes the piece and vice versa; removing a `CampaignNpc` deletes its occurrences and pieces on the campaign's maps; campaign deletion also removes `campaign_npcs` and the `map_npcs` of its deleted maps; tokens used by NPCs can't be deleted. Master writes; `GET /api/map/{id}/npc` for master + approved participants.
- Turns (feature 016): `campaigns.current_turn` (starts at 1) + `turns` log (`TurnType` Movement/Action/ActionResult; exactly one of `character_id`/`npc_id`, NPC entries from the map keep `map_npc_id` because each occurrence has its own turn). `MapTokenService.MoveAsync` records the Movement (before/after) for character/NPC pieces in the same transaction and answers 409 on a second move in the turn (objects are free). `TurnService`: read = master or approved participant; `POST /api/turn/action` and `/reset` = owner of the approved character or the master (NPCs master only, objects 400); reset deletes the actor's entries and moves the piece back only if the former hex is free; `POST /api/campaign/{id}/turn/finish` (master) lists approved characters without an Action unless `force`; `POST`/`DELETE /api/turn` are master-only and the only way to write an ActionResult. Deleting characters/NPCs/occurrences/campaigns deletes their turn entries first.
- Real-time table (feature 017): SignalR `TableHub` (`Roll6.Application/Realtime`, mapped at `/hubs/table` in `Program.cs`) is **server → client only** — every change still goes through the REST API. `[Authorize]`; the JWT comes from the `access_token` query string only on `/hubs` paths (`JwtBearerEvents.OnMessageReceived` in `Startup`). Clients call `JoinCampaign(campaignId)` (allowed by `ICampaignService.CanReadAsync` = master or approved participant; `HubException("forbidden"/"not-found")`) / `LeaveCampaign()`; each connection follows one campaign group `campaign:{id}` (`TableConnections`, in memory, single instance). Domain services publish a `TableEventInfo` (`type`, `campaignId`, `mapId`, `actorUserId`, `data`; types in `DTO/Realtime/TableEventType`, built with `Domain/Realtime/TableEvents.Create`) through `IRealtimeNotifier` (last constructor parameter) **after** the write succeeds; `SignalRRealtimeNotifier` logs and swallows failures. Piece moves/changes send the `MapTokenInfo` (`mapToken.upserted`/`deleted`); everything else is a reload signal (`mapTokens.changed` — null `mapId` = every map, `party.changed`, `campaignNpcs.changed`, `turn.changed`, `turn.finished`, `map.saved` per campaign using the model, `maps.changed`, `map.deleted`, `map.current`, `campaign.changed`, `campaign.deleted`). A player left without an approved character is removed from the group (`RemoveUserFromCampaignAsync`). `campaigns.current_map_id` (FK `fk_map_campaign_current`) + `PUT /api/campaign/{id}/current-map` (master) hold the map the players follow; deleting it clears it.
- Campaign plan (feature 018): `CampaignPlan` (`campaign_plans`, several entries per campaign, FK `fk_campaign_plan`) = title (≤ 260) + markdown description (`varchar(50000)`), `created_at`/`changed_at`; **master only** for every operation (`GET /api/campaign/{id}/plan` lists without descriptions; `GET`/`POST`/`PUT`/`DELETE /api/campaignplan`). Images in the text are stored as `roll6-image:{guid}.{ext}` (only the uploaded file name — presigned URLs expire) and the detail returns `imageUrls` (file → presigned URL) computed by `CampaignPlan.ImageFileNames()`. Campaign deletion deletes its plans.
- API keys (feature 019): `ApiKey` (`api_keys`) stores only `key_hash` (SHA-256 hex, unique) and `key_prefix` (`r6_` + 8 chars); the full key (`r6_` + 32 random bytes base64url) is returned once by `POST /api/apikey`. Authentication (`Roll6.Application/Auth`): the default scheme is the policy scheme `Roll6`, which forwards to the `ApiKey` handler when the request has `X-Api-Key` and to JwtBearer otherwise — so every `[Authorize]` accepts keys with the same `sub` claim (full access of the owner) plus `auth_method = api_key`. The `Session` policy (authenticated and not `api_key`, else 403 `ProblemDetails`) guards `ApiKeyController`, `PUT /api/user/name`, `PUT /api/user/password` and `TableHub`. `ApiKeyService.AuthenticateAsync` looks the hash up on every request (no cache → revocation is immediate), answers a generic 401 for unknown/malformed/expired/revoked keys and writes `last_used_at` at most once a minute; max 10 active keys per user (409); deleting needs a revoked/expired key (409); another user's key → 404. Services use the registered `TimeProvider` for "now".
- MCP server (feature 020): separate project **`Roll6.Mcp`** (own container `roll6-mcp`, `Roll6.Mcp/Dockerfile`, dev `dotnet run --project Roll6.Mcp` on http://localhost:5129) exposing the API to AI assistants at `/mcp` (Streamable HTTP, `ModelContextProtocol.AspNetCore` 2.x). It is a **thin gateway**: it references only `Roll6.DTO` and holds no database, S3 or JWT secrets — every tool is one REST call to the API (`Roll6Api:BaseUrl`, `http://api:8080` in containers) through `Roll6ApiClient`, which forwards the caller's `X-Api-Key` (or `Authorization`), so permissions, validation, results and the real-time events (017) are the API's. `ApiCredentialGate` answers 401 on `/mcp` without a credential the API accepts (checked via `GET /api/user/me`, cached 60 s). `McpToolRunner.FromResponseAsync` turns the API response into the tool result: JSON as text + `structuredContent` (lists inside `{ items }`, 204 → `{ ok: true }`), errors → `isError` with the API's problem details (plain-text/empty bodies get `status`/`detail`). Each tool (`Tools/*.cs`, `[McpServerToolType]`) carries `[ApiOperation("VERB", "/api/route")]`, an English `[Description]` with *What it does / Who can use it / Returns / Common errors / Related tools*, described parameters (`McpDocs`) and `ReadOnly`/`Destructive`/`Idempotent` annotations; `Roll6Guide` is the resource `roll6://guide`, the tool `get_roll6_guide` and the server instructions. **Adding or changing an endpoint requires its tool**: `Roll6.Tests/Mcp/McpCoverageTests` (every controller action except the 8 login-only ones has exactly one tool), `McpRouteParityTests` (each tool sends its `ApiOperation` verb/route with the caller's key, via `FakeApi`) and `McpDescriptionTests` guard it. Client setup: `claude mcp add --transport http roll6 https://{domain}/mcp --header "X-Api-Key: r6_…"`. The `web` nginx proxies `/mcp` to `mcp:8080`; the Vite dev server to `VITE_MCP_PROXY` (5129).
- `Roll6Context` configures every table inline in `OnModelCreating`; add one migration per change. The Npgsql legacy timestamp switch is on because columns are `timestamp without time zone` holding UTC. Int columns with DB defaults need `HasSentinel` so explicit zeros are persisted.

## Frontend layout and commands

React SPA in `frontend/` (design docs: `specs/006-frontend-map-editor/`). Dark theme only (`data-bs-theme="dark"` on `<html>`), every window besides the map is a modal, all feedback via `sonner` toasts, all texts via i18next (`src/i18n/locales/pt-BR.json`).

- Folder casing is from the constitution, not from the `react-architecture` skill: `src/Contexts/`, `src/Services/`, `src/hooks/`, `src/types/`. Services are classes whose private `handleResponse` delegates to `Services/apiHelpers.ts` (`handleApiResponse`: 401 → global logout handler; errors → message from `ProblemDetails`). Responses are the DTO itself — no `sucesso` envelope. API base is `VITE_API_URL` (`frontend/.env.local`, template `.env.example`); keep it **empty** so the app calls `/api` on its own origin — the Vite dev server proxies it to `VITE_API_PROXY` (5119 = `dotnet run`, 5000 = homolog API container), and nginx does the same in Docker. Never point `VITE_API_URL` at the homolog API from the dev server: that API has no CORS (Development only).
- Provider chain in `main.tsx`: `AuthProvider` → `CampaignProvider` → `RealtimeProvider` → `CharacterProvider` → `MapEditorProvider` → `TokenProvider` → `MapTokenProvider` → `NpcProvider` → `TurnProvider` → `App`. Session in localStorage `roll6:auth`, current campaign id in `roll6:campaign`, chosen character per campaign in `roll6:character` (`{ [campaignId]: 'gm' | characterId }`, cleared on logout). The open map is remembered in `roll6:map` (`{ mapModelId, mapId }`, written by `MapEditorContext` whenever another map is opened/saved, removed by "Novo mapa" and logout) and reopened after login/reload (`GET /api/map/{id}` for campaign maps; forgotten if deleted or inaccessible).
- `CharacterContext` holds the user's characters, their participations in the current campaign (`GET /api/campaigncharacter/mine`), the chosen character and the pending invites (polled every 60 s while the tab is visible). Pure rules (combo options, fallback, action per status) live in `lib/characterSelection.ts`. `CharacterSelect` ("Personagem atual") and `NotificationBell` are Radix Dropdown menus like `UserMenu`; the combo lists "Mestre (GM)" (master only) plus the user's own approved characters, then the Gerenciar/Selecionar/Incluir actions. Saving: own existing map → `PUT /api/mapmodel/{id}`; new map or someone else's (copy) → name modal → `POST /api/mapmodel` + `POST /api/map` when the user is master of the current campaign. `hooks/useUnsavedGuard.ts` owns the Save/Discard/Cancel guard used before switching maps, opening image+ and logging out.

The hex size is the fixed constant `HEX_SIZE = 40` (px, center→corner) in both `HexGrid.cs` and `lib/hexGrid.ts`; adjusting the image never changes the grid — the image moves/scales under it (negative offsets move it right/down, range ±20000). The backend lets the master move anything without limit and re-computes the cost for players (own approved character only, cost ≤ character move, else 400/403).

NPC fields live in `components/npcs/NpcFormFields` (round picture, required token via `TokenModal`, markdown sheet); rules in `lib/npcForm.ts`.
- Turns (016): `TurnContext` (after `NpcProvider`) holds the current campaign's `turnNo` + entries (master or approved participant only), polled every 15 s while visible; a higher `turnNo` becomes a "Turno N finalizado" bell notification (localStorage `roll6:turn-seen` = `{ [campaignId]: { known, unread } }`, cleared on logout) that opens `TurnSummaryModal`. Pure rules (card dot colors, NPC aggregation over its occurrences on the open map, `hasMoved`, balloons, trails) live in `lib/turnStatus.ts`. Map layers: `TurnTrailLayer` under the pieces, `SpeechBubbleLayer` (`foreignObject`) above them; `HexMenu` hides "Mover" once the piece moved and offers "Agir" / "Resetar turno"; "Turno N" is shown in the map footer (`GridSizeFooter`, next to the zoom) and `TurnControls` in `TopMenu` holds the master's "Finalizar turno".
- Real-time (017): `RealtimeContext` (`Services/realtimeService.ts`, `@microsoft/signalr`, token via `accessTokenFactory`) connects per session, joins the current campaign and hands its `tableEvent`s to subscribers (`hooks/useRealtime.useTableEvents`); after every successful (re)join it emits a local `resync` so every context reloads. It applies the campaign events itself (`campaign.changed`/`deleted`, `map.current` → new `currentMapId`) because `CampaignProvider` sits above it. `live` = connected **and** joined: while live, the 15 s polling of party, NPCs and turn stops (invites keep their 60 s poll); a refused join (no approved character yet) is retried every 30 s. `MapTokenContext` applies piece events with `lib/realtimeEvents.applyTokenEvent`; `useTokenMovement` cancels the Mover mode if the piece changes underneath. `MapEditorContext`: the master opening a map of his current campaign calls `setCurrentMap`; players follow `currentMapId` on entering the campaign (after the `roll6:map` restore, so it wins) and on every switch, may open other maps until the next switch, and never lose unsaved changes (toast instead); `map.saved` reloads the open model with `loadMapModel(..., { keepView: true })`, `map.deleted` closes it. The footer shows "Reconectando…"/"Sem tempo real" while not connected. The Vite dev server proxies `/hubs` with `ws: true`.
- Campaign settings (018): master-only gear next to "Campanha atual" in `TopMenu` opens `CampaignSettingsModal` (tab remembered in localStorage `roll6:settings-tab`; closes when the campaign changes) with Personagens (`components/campaign/ManageCharactersPanel`, extracted from `ManageCharactersModal`, which now wraps it), NPCs (`CampaignNpcsTab`: list + `NpcFormModal`/`NpcPickerModal`), Mapas (`CampaignMapsTab`: open through the unsaved guard → becomes the table's map, archive/reactivate via `mapService.update`, delete via `mapService.remove`, "Atual" badge) and Plano (`CampaignPlanTab`: list + editor; "Inserir imagem" uploads and inserts `lib/planImages.planImageMarkdown` at the cursor; unsaved changes are confirmed before switching plan/tab or closing). Plan markdown renders through `components/ui/planMarkdownOptions` (`MarkdownEditor imageUrls` / `PlanMarkdown`): `rehype-sanitize` with the default schema + the `roll6-image` protocol in `src`, raw HTML skipped, and `urlTransform` (which runs after the sanitizer) resolving references to `imageUrls` — `components/ui/planMarkdown.test.ts` pins that scripts, handlers and `javascript:` never render.
- API keys UI (019): "Chaves de API" in `UserMenu` opens `ApiKeysModal` (state in `TopMenu`): name + expiration (7/30/90/365 days, specific date = end of that day in Brasília UTC−3, or never — `lib/apiKeyForm.ts`), the full key shown once with "Copiar" (forgotten on close), and a table with prefix, dates, last use, status badge, revoke/delete with confirmation. Backend dates are UTC without zone: read them with `lib/apiKeyForm.parseUtc`.
- Icons: only Bootstrap Icons, inlined as SVG components in `components/ui/icons.tsx` (`currentColor`, `size` prop; copy the path from the official SVG of the same name). Never emoji/Unicode symbols or per-file icon definitions; icon-only buttons carry `title` + `aria-label`.

Workflows copied from AvaBot: `version-tag.yml` (GitVersion, `GitVersion.yml`, tags `vX.Y.Z` on `main`; `feat:`/`minor:` bumps minor, `fix:` patch, `breaking:` major) and `create-release.yml` (GitHub release when major/minor changes).

- Startup migrations are toggled by `Database:ApplyMigrationsOnStartup`.
- Docker must not be run on the dev machine (constitution); compose files are for homolog/prod hosts.
- The `web` service (`frontend/Dockerfile`: Node build → nginx) serves the SPA built with `VITE_API_URL=""` and proxies `/api` and `/hubs` (WebSocket upgrade, long timeouts) to `api:8080` and `/mcp` (no buffering) to `mcp:8080` (`frontend/nginx.conf`), so homolog/prod are same-origin and need no CORS (CORS stays Development-only). Homolog: SPA on `WEB_PORT` (8080), API/Swagger on `APP_PORT` (5000), MCP on `MCP_PORT` (5100). Production (like AvaBot): no published ports, no database container and no `web` container — only `roll6-api` and `roll6-mcp`, both on the external `emagine-network`.
